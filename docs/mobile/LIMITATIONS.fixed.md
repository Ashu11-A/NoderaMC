**Category:** mobile · **Last audit:** 2026-07-28

Four rows retired on 2026-07-28: the Android bytecode guard now runs in CI (and caught a live
regression on its first run), the SDK pins agree, a tracker store reaches a running worker, and the
Restart button is no longer offered where nothing can honour it.

| id | Was | Retired by | Evidence |
|---|---|---|---|
| M-5 (guard) | Java 21 type-pattern switches could re-enter the worker's closure unnoticed — ART has no `SwitchBootstraps`, D8 cannot desugar it, and the guard against it was a script nobody was obliged to run | Wired into CI. `.github/workflows/build.yml` gains an `android-bytecode` job: it builds the real worker distribution, dexes the whole closure with build-tools 35's `d8`, and fails the build on a single `invoke-custom` site. The script also stopped reusing a stale distribution — it rebuilt only when `build/install` was missing, so it could report yesterday's answer about today's sources | The job's first run was RED: `MessageRouter.answerFor` had grown a type-pattern switch, on the message path, where it would have crashed the phone on the first frame answered. Rewritten as an `instanceof` chain; `scripts/check-android-bytecode.sh` then reported `0 invoke-custom sites, 0 SwitchBootstraps references` locally and in CI |
| M-9 | The generated Gradle project targeted SDK 36 while the toolchain script installed platform 34, so a machine provisioned only by that script downloaded platform 36 (and asked for its licence) mid-build | `scripts/android-toolchain.sh` pins `COMPILE_SDK=36`, matching what `gen/android/app/build.gradle.kts` compiles and targets. It also installs build-tools **35.0.0** beside 34.0.0 — `d8`/`dexdump` for the worker's dexing and for the bytecode guard, which the script had never installed even though two other scripts required them | `scripts/android-toolchain.sh` run green: `platform 36 yes · build-tools 34.0.0 yes · build-tools 35.0.0 yes` |
| M-NET-1 | "The synchronised services list is read once, at worker boot", so a tracker store added in the app was believed to take effect only next launch | The boot file was never the live path. The app merges every store's trackers into `network.default_trackers` and pushes them over `NODERA-CONFIG`; the worker applies that key straight to the ONE shared `TrackerClient`, which reaches the archive, hosting, discovery and replication lanes at once. Nothing in that chain is desktop-only — on Android the push crosses the same control endpoint into a worker in the app's own process | Both halves are now asserted: `config.rs::a_stores_trackers_are_pushed_to_a_running_worker` (a store's trackers reach the payload) and the new `ConfigVerbIT::aStoresTrackersChangeWhichTrackerARunningWorkerDials` (a running worker's dialled endpoints change, and a later push *replaces* the list rather than appending, so removing a store stops the dialling) |
| M-NET-3 | The Restart button was offered on a phone and did nothing | `daemon::ownership` reported `can_restart` from attach mode alone, but the signal's only consumer, `daemon::supervise`, is `#[cfg(desktop)]` — and on Android the worker is a thread in this very process, which cannot cycle itself. `can_restart` is now `!attached && cfg!(desktop)`, `restart_worker` answers with a sentence instead of a no-op, and the Settings banner says "Close and reopen the app to apply these" rather than the attach-mode line about restarting it where you started it | `restart_is_never_offered_where_nothing_consumes_the_signal` and `every_refusal_names_a_thing_the_user_can_actually_do` in `rust/nodera-app/src/daemon.rs` |
| M-8 | The worker booted on Android but died the moment it encoded its first peer-to-peer message, taking the app with it | Java 21 **type-pattern switches** compile to an `invokedynamic` on `java.lang.runtime.SwitchBootstraps`. ART does not implement it (`BootstrapMethodError` → `ClassCastException`) and D8 cannot desugar it (below API 26 it substitutes a stub that throws "Instruction is unrepresentable in DEX V35"). Every such switch in the worker's closure is now an `instanceof` chain | Phone `sent` 0 → 465 on the first encode, then a full session: phone `received=21534 peers=1`, Linux peer listing `0f0b34b4-… 10.0.0.104:25620`; `scripts/check-android-bytecode.sh` reports 0 invoke-custom sites |
| M-0 | "The Java worker cannot run on Android: `SwitchBootstraps.typeSwitch` is absent from ART and D8 cannot desugar it; rocksdbjni/zstd-jni ship desktop natives." | Measuring instead of asserting. The blocker was the **D8 version** (build-tools 34's R8 8.2 refuses Java 21 class files); build-tools 35 dexes the whole closure. The native libraries are never loaded on the worker's path. The one real incompatibility — virtual threads that exist and throw — is handled by `Threads`. | `NODERA-OK 2 0.1.0` and a full `NODERA-STATE` from `127.0.0.1:25610` on the device; `ThreadsTest` |
| M-5 (2026-07 crash) | The app crashed a few seconds after launch | `fresh_seed()` read `/dev/urandom` with `fs::read`, which reads to EOF | Native heap 2.5 GB → 14 MB; `a_fresh_seed_is_bounded_and_unpredictable` |
| M-6 | The first-run setup reappeared on every launch | Settings resolved to `/` on Android, so nothing persisted | `dirs_config()` Android arm + `SettingsHandle::reload()`; setup asked once across force-stops |
| M-7 | System back closed the app instead of going up | `TauriActivity` sets `handleBackNavigation = false` | `MainActivity` overrides it; back from Settings › Appearance returns to the list with the app still running |
